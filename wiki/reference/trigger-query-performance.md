# 触发器查询性能与结果对照

2026-10-07 在同一 Windows/Python 环境、同一官方资料输入上测量 `--reference examples waves`。索引包含 122 份 GUI 定义文档、108 份 Triggers（其中战役 106 份）。旧实现使用索引 v1，新实现使用 v2；重建后进行测量，不把构建耗时计入查询。

使用 `time.perf_counter` 计时、`tracemalloc` 记录 Python 分配峰值，并计数 `Document.__init__`。输出重定向到内存后解析以检查结果。以下各模式各测一次，不能据此宣称稳定加速；峰值不是进程 RSS，包含 XML 解析和输出序列化。

测量时精选案例库为七个入口；后来增加的对白案例未纳入这次计时。此表保留当时输入范围，不作为当前全部 27 个案例的性能保证。

| 模式 | 修复前秒 | 修复后秒 | 修复前峰值 MiB | 修复后峰值 MiB | 前/后解析文档数 |
|---|---:|---:|---:|---:|---:|
| summary | 4.850 | 4.555 | 131.66 | 137.27 | 2 / 2 |
| 最多展示 200 节点 | 4.718 | 4.542 | 131.39 | 137.00 | 2 / 2 |
| 展示全部 | 4.791 | 4.650 | 131.00 | 136.62 | 2 / 2 |

各模式前后均检查 365 个唯一元素、166 项资源，引用错误为 0；新实现三种模式的完整所需外部库集合均为 Ntve。摘要仍检查完整引用链；节点上限只控制展示存储。回归另外验证展示范围之外的缺失定义仍导致失败。

本案例查询耗时略低，峰值内存略高，没有证据证明总体内存下降。v2 同时保留中文和英文名称，新增了名称开销；小案例的峰值主要受官方 XML 解析影响。当前优化避免保存摘要的完整展示树，复用单次查询的解析/提供者结果，并使目标 find 在取得足够可用结果后停止兼容性分析；本案例仍必须解析两份文档，不能报告减少解析次数。

所有缓存仅属于当前查询，不保存长期兼容性结论。参考源与依赖变更仍执行新鲜度检查。实际编辑器与打包运行性能不在此测量范围内。
