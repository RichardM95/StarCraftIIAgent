# GalaxyScript usage in the Starcraft II Editor

## Overview
GalaxyScript is the programming language of the SC2 editor. While most of it is hidden behind the GUI layer of the Trigger Editor, all your trigger work eventually boils down to GalaxyScript, autogenerated by the Editor in your MapScript.galaxy.
A lot of things in the editor boil down to either Strings or Ints. Dialogs and Dialog Items, for example, are just Integers. Unit Types (or 90% of Data References, really) are just Strings. There’s a lot of times when the editor forces you to convert between the many inbuilt types. This can be especially annoying when dealing with Game Links, as they often slow down or lag out the game.

## Usage Tutorial: Creating your first Script
Open your map in File Explorer, and create a folder called scripts. This will be where we put all the galaxy files.

Create a file called UI.galaxy. As I mentioned before, the “Create Dialog Item From Template” function likes to crash my editor. Let’s write a wrapper function so we can create Dialog Items from a string instead.

In the file, copy/paste (or write) the following code snippet:
```galaxy
int CreateDialogItemFromTemplate(int dialog, int type, string template)
{
    return DialogControlCreateFromTemplate(dialog, type, template);
}
```

Next, we need to import this into the editor so we can use it. Start by creating a Custom Script Object (Ctrl+Alt+T). Name it imports. Then, add the following line to it:
```galaxy
include "scripts/UI"
```

Custom Script just appends the script to the top of the MapScript.galaxy when generated. (If you’ve ever done any work in C/C++, it’s like #include <stdio.h>) This allows us to use functions from that file in the ‘main’ script, and all other scripts that come after it.

Now, let’s create a native function so we can actually use the script we wrote. Create a new function and name it the same thing as the function in the script: CreateDialogItemFromTemplate. Open the function options, then check the box that says Native Function. Since it’s returning a Dialog Item, set the return value to Dialog Item. Then, we’ll create the parameters.
-Dialog is an int, but you should remember that Dialogs are just integers. So its type is Dialog.
-Type is a preset: the type of the Dialog Item.
-Template is a string.

Then, let’s test it. I create a dialog item and create a button in it using our function. Let’s fire up the test map and we are finished.
Admittedly, what we did above was incredibly easy to do in the GUI as well, but it was more for demonstration purposes.

When deciding when to write script vs GUI, I have a few rules of thumb:
1. Write only self-contained functions. Referring to global variables is doable (just add a gv_ prefix before their name), but it’s generally good practice not to. The one exception to this rule is constants, but that should be obvious.
2. Do any catalog related work in Galaxy. The GUI functions are annoying and working with strings is a lot easier than working with game links.
3. Annoying type conversions or frequently repeated (loops won’t work) should be done in Galaxy.
4. Trigger creation should always be done in GUI.

## Grammar Specifications and Syntactic Rules

Galaxy Script is a statically typed, imperative language that syntactically resembles C. However, it lacks many modern C/C++ or C# constructs. Violating Galaxy's constraints will cause compile errors or engine script crashes:

1. **Local Variable Scope Hoisting:** All local variables inside a function must be defined at the absolute beginning of the function body, preceding any executable statements, assignments, or function calls. Declaring variables after statements or inside inline block scopes (such as within `if`, `while`, or `for` blocks) is a fatal syntax error.
2. **Increment / Decrement Operators:** Post-increment (`i++`) and post-decrement (`i--`) are unsupported. You must use explicit compound assignments (`i += 1;` or `i -= 1;`).
3. **Include Directives:** Paths must be declared relative to the root directory **without file extensions**. Writing `include "Scripts/Utility.galaxy"` or `#include "Scripts/Utility.h"` causes a compilation failure, whereas `include "Scripts/Utility"` resolves correctly.
4. **Data Link Representation:** While GUI triggers use typed wrapper objects like `gamelink`, raw Galaxy Script interacts with catalog entries, abilities, and unit types using primitive `string`, and UI/dialog handles using primitive `int`.
5. **Memory and Structs:** Structs and arrays are pass-by-reference. Galaxy lacks dynamic heap allocation via pointers (`malloc`/`new`). Avoid infinite recursive structures.
6. **Asynchronous Logic and Multithreading:** Galaxy functions execute on a single main thread by default. Long-running loops or blocking calls like `Wait()` will lock execution or exceed engine operational limits (`TriggerExecutionLimit`) unless spawned into separate threads via native triggers or multithreaded Action Definitions.

### Syntax Comparison

| Language Feature | Standard C / C++ / C# Syntax | StarCraft II Galaxy Script Standard | Engine Consequence of Failure |
|---|---|---|---|
| **Local Variable Scope** | Declared anywhere within a block scope. | Hoisted to top of function body before any statements. | Fatal compilation error (`Unexpected token/symbol`). |
| **Increment / Decrement** | `i++;` or `++i;` | `i += 1;` or `i = i + 1;` | Syntax error during parsing pass. |
| **Include Paths** | `#include "Scripts/Header.h"` | `include "Scripts/Header"` (no extension) | File open failure / Include target not found. |
| **Data Link Representation** | Typed classes or Enum definitions | Primitive `string` (Catalogs) or `int` (UI/Dialogs) | Type mismatch error during function invocation. |
| **Asynchronous Logic** | `async` / `await` or Thread pools | Native Triggers / Multithreaded Action Definitions | Engine script thread freeze / Operations limit exceeded. |

### Variable Hoisting Example

```galaxy
// INCORRECT: Variable declared after executable statements (causes fatal compile error)
void gf_ExecuteTacticalStrike_Bad(int lp_player, point lp_target) {
    UnitCreate(1, "Marine", 0, lp_player, lp_target, 270.0);
    unit lv_createdUnit = UnitLastCreated(); // FATAL ERROR: Declaration after statement
    lv_createdUnit += 1;
}

// CORRECT: Compliant Galaxy Script syntax
void gf_ExecuteTacticalStrike_Good(int lp_player, point lp_target) {
    // 1. Variable declarations hoisted to the top of the function
    unit lv_createdUnit;

    // 2. Procedural execution logic
    UnitCreate(1, "Marine", 0, lp_player, lp_target, 270.0);
    lv_createdUnit = UnitLastCreated();

    // 3. Increment operation using compound assignment
    // (Note: variable assignment and operations follow variable declarations)
}
```

## API Architecture & Namespaces

The StarCraft II scripting environment is divided into three distinct operational tiers:

1. **Engine Natives:** Core primitives exposed directly by the engine executable (e.g. `UnitCreate`, `OrderTargetingPoint`, `CatalogReferenceGet`, `UnitBehaviorGet`, `UnitKill`, `ActorSend`).
2. **Standard Native Helpers (`libNtve`):** Wrapper functions compiled into `libNtve_gf_*` that provide simplified interfaces for common actions (e.g. `libNtve_gf_SetFacing`, `libNtve_gf_UnitInRegion`, `libNtve_gf_CinematicMode`).
3. **Campaign Support Libraries (`libCamp`):** Specialized functions (`libCamp_gf_*`) handling campaign story engines, mission objectives, transmissions, cinematic cutscenes, and planet panels.

### API Module Domain Reference

| API Module Domain | Primary Function Namespaces | Functional Scope & Execution Context |
|---|---|---|
| **Core Engine Logic** | `UnitCreate`, `UnitKill`, `OrderApply`, `OrderTargetingPoint` | Instantiates units, applies spatial movement orders, and manages core unit life states. |
| **Actor Infrastructure** | `ActorSend`, `ActorCreate`, `libNtve_gf_SetFacing` | Controls client-side visual actors, model swaps, facing directions, and animation brackets. |
| **Catalog Reflection** | `CatalogReferenceGet`, `CatalogFieldValueSet` | Performs dynamic runtime queries and mutations against GameData XML catalog elements. |
| **Behavior & State** | `UnitBehaviorAdd`, `UnitBehaviorGet`, `UnitBehaviorHas`, `UnitBehaviorRemove` | Queries or modifies unit behavior stacks, status effects, and attributes dynamically. |
| **Campaign Systems** | `libCamp_gf_SendTransmission`, `PlanetCreate` | Drives story engine sequences, planet selection panels, UI objectives, and transmissions. |
| **UI & Dialog Engine** | `DialogCreate`, `DialogItemCreate`, `DialogSetPosition`, `DialogControlHookup` | Constructs custom user interface elements, buttons, text fields, and frame hooks. |

## Runtime Catalog Reflection (CatalogFieldValueSet / CatalogReferenceGet)

When manipulating catalog values dynamically at runtime via Galaxy Script, field paths must use dot-notation string syntax mirroring the internal XML element tree structure:

```galaxy
// Dynamically adjusting catalog attributes at runtime
// The field path strictly mirrors the XML element tree structure
void gf_UpgradeUnitArmor(string lp_unitType, int lp_player, int lp_bonusArmor) {
    string lv_fieldPath;

    // Constructing raw path: corresponds to <CUnit><Armor value="..."/></CUnit>
    lv_fieldPath = "Armor";

    // CatalogFieldValueSet(Catalog, Entry, FieldPath, Player, Value)
    CatalogFieldValueSet(c_gameCatalogUnit, lp_unitType, lv_fieldPath, lp_player, IntToString(lp_bonusArmor));
}
```

## Evaluating Data Validators from Galaxy

Use `ValidatorExecute` when trigger or tactical-AI logic needs to run one Data validator directly. Its arguments are the validator link, source unit, and target unit:

```galaxy
bool MyValidatorAcceptsTarget(unit source, unit target) {
    return ValidatorExecute("SomeValidator", source, target) > 0;
}
```

Use `UnitValidateEffectUnit` when the question is whether an entire Effect, including its validator chain, accepts a caster/target pair. `UnitValidateEffectPoint` handles point targets; `PlayerValidateEffectUnit` and `PlayerValidateEffectPoint` cover checks without a caster unit. These Effect-validation natives use the command-error convention, where `0` means accepted:

```galaxy
bool MyEffectAcceptsTarget(unit caster, unit target) {
    return UnitValidateEffectUnit(caster, "SomeEffect", target) == 0;
}
```

Do not interchange the success tests: direct `ValidatorExecute` and Effect validation use different result conventions.

Source and scope: Blizzard's installed Xel'Naga tactical-AI script rejects `ValidatorExecute` results at or below `0`; the installed native helper library implements its four `Player/Unit Can Create Effect` conditions by comparing Effect-validation results to `0`. The repository's generated native tables confirm both APIs and their argument types.


## Examples
Here are some general, all purpose utility/example actions. All variable names are meant to be self-explanatory. Anything starting with c_ is a preset.

### Traversing player groups
```galaxy
void DisplayMessageToPlayerGroup(string message, playergroup group)
{
    int player;

    for(player = 1; player <= CONST_MAX_PLAYERS; player+=1)
    {
        if(!PlayerGroupHasPlayer(group, player)){ continue; }
        UIDisplayMessage(PlayerGroupSingle(player), c_messageAreaChat, StringToText(message));
    }
}
```

### Dynamic Function Registration
```galaxy
void CreateButtonAndRegisterToTrigger()
{
    // Create the Dialog Item
    int dialogitem = libNtve_gf_CreateDialogItemButton(
        CONST_DIALOG,
        300,
        75,
        c_anchorCenter,
        0,
        0,
        StringToText(""),
        StringToText("Click Me!"),
        ""
    );

    // Add it to global trigger TRIGGER_VARIABLE
    TriggerAddEventDialogControl(
        TRIGGER_VARIABLE,
        c_playerAny,
        dialogitem,
        c_triggerControlEventTypeClick
    );
}
```

### Creating a Trigger / Creating an async function
```galaxy
trigger MyGlobalTrigger;

// You can name these variables whatever you want; testConds/runActions is just the standard.
bool MyTrigger(bool testConds, bool runActions)
{
    // Echoes the chat message back to the player
    UIDisplayMessage(PlayerGroupSingle(EventPlayer()), c_messageAreaChat, StringToText(EventChatMessage()));

    return true;
}

void MyTrigger_Init()
{
    // Use the name of the function you want to execute as an argument
    MyGlobalTrigger = TriggerCreate("MyTrigger");
    TriggerAddEventChatMessage(MyGlobalTrigger, c_playerAny, "echo", false);
}
```

### Scope
```galaxy
// This function cannot be accessed outside of this file
static bool ThisIsTrue()
{
    return true;
}


// This function can
bool TrueIsTrue()
{
    if(!ThisIsTrue())
    {
        return false;
    }
    else
    {
        return true;
    }
}
```

### Useful functions (confirmed)

#### Cinematic mode — full wrapper (USE THIS to restore cursor/HUD)
```galaxy
// Signature: void libNtve_gf_CinematicMode(bool lp_onOff, playergroup lp_players, fixed lp_duration)
// Caches UI state on turn-on and RESTORES it on turn-off (cursor, HUD, UISetMode).
// Use this when turning off cinematic mode before showing a dialog.
libNtve_gf_CinematicMode(false, PlayerGroupAll(), 0.0);
```
Reference: https://mapster.talv.space/galaxy/reference/lib-ntve-gf-cinematic-mode

#### Cinematic mode per-player — internal toggle only (does NOT restore cursor/HUD)
```galaxy
// Signature: void libNtve_gf__CineModeTurnOnOffForPlayer(int lp_player, bool lp_onOff)
// Note the double underscore after gf_. Marked internal — only toggles the flag,
// does NOT restore cached UI state. Mouse cursor stays hidden if UISetMode was set
// to fullscreen. Do NOT use this when a dialog must follow.
libNtve_gf__CineModeTurnOnOffForPlayer(1, false);
```
Reference: https://mapster.talv.space/galaxy/reference/lib-ntve-gf-cine-mode-turn-on-off-for-player

#### Tactical AI Functions

Units can be given custom AI logic via two paths:

**Path A — Data Editor (simple rules):** In the Data Editor → Units tab, find `AI: Tactical AI Data` to create rule-based behaviour (e.g. "use EMP if target shield > 100") without any scripting.

**Path B — Galaxy script (full control):**

1. In the Data Editor → Units tab, set `AI: Tactical AI Function` to the name of your Galaxy function.
2. Write the function in Galaxy. It must have the signature `bool MyFunc(unit u, player p)`. Return `true` if an action was taken (prevents default AI from running), `false` to fall through.
3. Register the function in a map-init trigger using `libNtve_gf_SetTacticalAIThink`.

```galaxy
bool MyTacticalAI(unit u, player p) {
    if (UnitGetPropertyInt(u, c_unitPropLifePercent, c_playerAny) < 20) {
        AICast(u, Order(AbilityCommand("move", 0), Point(10, 10)));
        return true;
    }
    return false;
}
```

**Key caveats:**
- If a trigger issues an order to the unit (e.g. `IssueOrder`), the unit becomes "Script Controlled" and may ignore tactical AI data.
- A generic pattern: loop over a unit's abilities and call `AIExecuteAbilTactical` rather than writing per-unit-type logic.
